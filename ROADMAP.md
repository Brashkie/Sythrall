## Language philosophy

Sythrall isn't "built with six languages" — each language sits at the layer where it
actually earns its place, and Phases 13+ below are organized around that split
instead of a flat "add more languages" list:

| Layer | Language | Role | Evidence so far |
|---|---|---|---|
| Interaction | **TypeScript** | UI, Monaco integration, editor intelligence, diagrams — the only layer a user directly touches | Vite + Monaco + Mermaid + Chart.js + xterm, all shipped (Phases 1–9) |
| Intelligence & Science | **Python** | AI/ML detection, orchestration, scientific workloads — **not** the static-analysis engine long-term: that role is being retired to Rust (Phase 18's Native Analysis Core), one measured slice at a time | 23 library detections, ML/DL Inspector (Phase 2). `static_parser.py` itself is the legacy piece Phase 18 is migrating out of Python, not a permanent fixture |
| Native Analysis | **Rust** | The static-analysis engine, committed destination — parsing, AST, symbol resolution, complexity, security, quality, graphs. Each slice is still profiled/benchmarked before the swap (that's *how*, not *whether*) | `terminal-server` (PTY handling), `complexity-engine` (9–21× faster than `radon` — Phase 11), rich Python analysis ported (Phase 18) |
| Legacy ecosystem/interop | **C/C++** | Analysis target (shipped, Phase 18) — reading and fully understanding existing C/C++ systems for what they are: security, memory layout, complexity, architecture, dependencies. Since 2026-08-30, also the primary raw material Phase 25's Modernization Intelligence works from — not to replace C/C++ everywhere, but to identify which specific pieces of a legacy system are candidates for Rust/Zig/modern C++, backed by evidence the analysis above already computes, never a blind convert | Shipped (Phase 18) — `cparse.rs`; `memlayout.rs` (Phase 23) feeds the ownership/RAII candidates Phase 25 will use |
| Scientific/HPC | **Fortran** | Analysis target (shipped) **and**, since 2026-08-30, an open candidate for real implementation inside Sythrall's own engine — not just numpy/scipy's free LAPACK/BLAS speed, but Fortran Sythrall itself writes, wherever a measured numerical hot spot justifies it. `fortran_bench.rs`'s validation kernel is the first proof this is more than theory: Sythrall already compiles and runs real Fortran for its own purposes, not just to read someone else's — and as of 2026-08-30 that kernel is a real, standalone `.f90` file in the repo (`kernels/validate_matmul.f90`, pulled in via `include_str!`), not a string literal buried inside Rust source. The fuller shape this is heading toward (Phase 26): a prototype written in Python, a real numeric kernel in Fortran once the shape is proven, Rust orchestrating the call, Assembly only for the single hottest inner loop if profiling still justifies it after all of that | Shipped (Phase 20) — `fparse.rs`, `tree-sitter-fortran`, `fortran_bench.rs` (Phase 23), `kernels/validate_matmul.f90` |
| Machine-level | **Assembly** | Analysis target — pattern-matching on raw `.s`/`.asm` text shipped (Phase 19's first bullet); wrapping Capstone/LIEF over real executables (PE/ELF/Mach-O) still planned — **and**, since 2026-08-30, an open candidate for hand-written hot paths inside Sythrall itself, but deliberately the *last* rung of a ladder, not a first resort: Rust first, then Zig/C if Rust's abstractions are themselves the bottleneck, and only Assembly once profiling shows a compiler genuinely can't close the gap — SIMD, CPU-specific instructions (AVX2/AVX-512/NEON), crypto primitives, a specific hot loop, never "rewritten in ASM because ASM is fast" | Shipped (Phase 19, 1st bullet) — `asmparse.rs`. **Actually profiled, not just left open** (2026-08-30): `cargo bench --bench complexity_bench` on 1000 functions runs in ~96ms (~96µs/function) — parser/tree-walk overhead, not a dense numeric loop SIMD would help with. No implementation-language use — honestly, no candidate found yet, not merely "none looked for" |
| Native tooling | **Zig** | Build/cross-compilation/standalone distribution (Phase 29, renumbered 2026-08-30 — see "Where this is going, next" below) **and**, since 2026-08-30, a real candidate for low-level components themselves — codecs, C interop, native tooling pieces that want maximum control with minimal abstraction, not only the toolchain wrapping Rust's own binaries. **The guardrail that keeps this from becoming decoration**: never "this is in Zig because Zig is fast" — only "this is in Zig because it needs memory/ABI/toolchain control or C interop that makes the component itself simpler here than in Rust," a real technical reason stated up front, not retrofitted | **Shipped (Phase 29, 2026-08-30)** — `scripts/cross-compile.sh`/`.ps1`, `cargo-zigbuild` cross-compiling `complexity-engine`/`terminal-server`; verified end to end on this dev machine (Windows → real Linux ELF binaries, confirmed with `file`, not just "it compiled"). Not yet used as the language for a component's own logic — only as the cross-compilation toolchain so far |

The rule for moving anything into Rust (or any native language) used to be a real
either/or: profile first, benchmark the replacement, keep it only if the numbers
justify it — Phase 10's large-project investigation found the real O(n²) cost was
three ordinary Python bugs, not the parser, and fixed it without a new language;
Phase 11's `complexity-engine` found a real, measured 9–21× win and adopted Rust.
Both outcomes came from the same process; neither was assumed going in.

For the static-analysis engine specifically, that question is now settled: it's
moving to Rust, fully, not just wherever a benchmark happens to favor it — see
Phase 18's Native Analysis Core below. What survives from the old rule is the
*method*, not the *decision*: each slice is still ported, parity-tested against
the Python it replaces, and benchmarked before the call sites switch over, so the
migration never trades correctness for the sake of hitting the target faster. The
either/or framing still applies to any *other* future native-language adoption
outside this specific migration — this is a one-time, explicit exception, not a
reversal of the general rule.

**Philosophy update (2026-08-30), confirmed explicitly with the user, not assumed**:
Fortran, Assembly, and Zig stop being purely "analysis target"/"separate toolchain
concern" and become real candidates for *implementing* pieces of Sythrall's own
engine — not a decision to actually rewrite anything yet, just removing the
blanket "never an implementation language" framing the table above used to state
for Fortran/Assembly. **The same either/or rule from Phase 10/11 governs this
exactly as it would a new Rust adoption**: profile first, find an actual
bottleneck or a genuine low-level-control need, benchmark the alternative,
adopt only if the numbers (or the capability gap) justify it — no speculative
rewrites "because the language exists." No concrete candidate has been profiled
or scoped yet for Assembly or Zig as implementation languages; Fortran already
has one small proof point (`fortran_bench.rs`'s validation kernel, Phase 23),
though that was written to validate a *static claim*, not because a Sythrall
hot path itself needed Fortran's numeric performance.

## Where this is going: Computer Science Intelligence, not a linter

The honest one-line description of Sythrall today is "reads code, computes Big-O."
Phases 13–23 below are the plan for growing that into something more specific:
*Sythrall analyzes software from the mathematical/algorithmic structures underneath
it, through to the compiler, the machine code, and the hardware it runs on.* Not by
becoming a math solver or a compiler — by connecting the CS theory that already
explains *why* Sythrall's existing heuristics work (Big-O, the Chomsky-hierarchy
classifiers from Phase 8/12, the Lambda-Calculus framing on tail recursion) to the
rest of the theory those ideas come from, and building detectors for it the same
heuristic, benchmark-first way everything else in this roadmap got built:

```
                    Computer Science Engine
                              │
        ┌─────────────────────┼─────────────────────┐
        │                     │                      │
   Algorithms             Mathematics             Languages
        │                     │                      │
    Big-O/Θ/Ω            Discrete Math          Formal Languages
    Data Structures       Logic                 Grammars
    Graphs                Recurrences           Parsing Theory
        │                     │                      │
        └─────────────────────┼──────────────────────┘
                              │
                       Compiler Theory
                              │
                    Lexer → AST → IR → Codegen
                              │
                        Machine Code
                              │
                             CPU
```

Each layer below is still gated by the same rules already established in this
roadmap: heuristic and explicit about it (matching the WASM-hint/CS-Engine-classifier
style, not claiming semantic proof), and any native-language adoption still requires
its own before/after benchmark (Phase 18's rule, proven twice already).

### ✅ Phase 8 — Computer Science Engine *(direct extension of the existing analysis engine, no new architecture)*

Not just "what" the code does — *why* it behaves that way. Built entirely on data `static_parser.py` and the Big-O engine already compute:

- [x] Full complexity picture per function: Θ (tight bound), Ω (best case), O (worst case) — not just worst-case O *(Python only for now; C/C++/JS/TS still show O only)*
- [x] "Why" explanation attached to every Big-O result (e.g. *"2 nested loops — inner loop runs n times per outer iteration"*)
- [x] Recursion detected → tail-call detection + "Lambda Calculus" framing *(recursion-depth estimate skipped — depends on runtime input, not reliably computable statically)*
- [x] Regex detected → classify as Finite Automaton / Chomsky Type-3 (Regular) *(direct `re.XXX(...)` calls only — doesn't trace a `re.Pattern` saved in a variable)*
- [x] Grammar/parser-shaped code detected → Context-Free Grammar / Pushdown Automaton / Chomsky Type-2 *(heuristic: name keyword + recursion/explicit-stack shape — both signals required to keep false positives down)*
- [x] Graph traversal detected → label as DFS/BFS/topological sort, O(V+E) *(heuristic: variable-name signals — `visited`/`seen`/`explored`, `in_degree`, a queue with `.popleft()` — not real data-flow analysis)*

### ✅ Phase 9 — Integrated Terminal + Folder Explorer + Theme

Not originally on this roadmap — came directly from user feedback mid-development, folded in because each piece was small and well-scoped on its own:

- [x] **Integrated terminal**, real interactive shell over WebSocket — first use of **Rust** in the project (`terminal-server` sidecar: `portable-pty` + `axum`), token-protected, zero-friction auto-connect for local use, panel switcher between the shell and a live Logs view
- [x] **Folder explorer** in the sidebar ("+ Folder") — VSCode-style expandable tree from a real disk folder, cross-browser via `webkitdirectory` (deliberately *not* the File System Access API, which is Chromium-only)
- [x] **Light/dark theme** toggle, persisted, dark by default
- [x] [`ansimax`](https://github.com/Brashkie/ansimax) (own library) for the `npm run dev` startup banner, later reused for the terminal panel's own welcome banner (see the "Terminal v2" bullet below)
- [x] **Terminal v2 — multi-session tabs, shell picker, branded prompt, real VSCode-parity chrome**: the original terminal was a single global shell with no tabs — each browser tab of Sythrall could only ever have one shell running. `terminal-server`'s `handle_socket` already spawned one independent `PtySession` per WebSocket connection, so multi-tab needed zero backend architecture change — the frontend just opens N sockets instead of reusing one (`components/terminal.ts`, full rewrite from a module-level singleton to a `TermSession[]` array).
  - **Virtual, workspace-relative prompt (`$sythrall>`, `$sythrall/proyecto>`)** — not just a `Sythrall` prefix in front of the real OS path. Sythrall is headed toward being a SaaS/cloud product, and the real filesystem path of whatever machine happens to be hosting it (`C:\Users\PC` today, some container path tomorrow) isn't information an end user should see. `pty_session.rs::workspace_root()` captures the directory `terminal-server` itself was launched from (the same for every session that process spawns) once; `build_command` re-derives, on every prompt render, the current directory *relative* to that root — `$sythrall` at the root, `$sythrall/apps` after `cd apps`, `$sythrall/apps/web` a level deeper — and falls back to showing the real absolute path prefixed `$sythrall:` only if the user navigates outside the root entirely (never silently lies about where they are). Passed as a startup **argument** to the shell (`powershell.exe -NoLogo -NoExit -Command "function prompt {...}"` recomputing `$rel` from `$PWD.Path` on each call; `bash` via `PROMPT_COMMAND`, re-evaluated before every prompt the same way; `cmd.exe`'s `prompt` mini-language has no conditionals or string ops at all, so it keeps a plain absolute-path prompt), never as bytes written to the PTY after spawn. The first version tried writing the prompt-setup command to the PTY right after spawning — verified by hand that it produces a visible "flash": the shell isn't reading stdin yet, so its line-editor (PowerShell's PSReadLine, specifically) echoes those bytes on screen as if the user had typed them, before the real prompt appears. Passing it as a launch argument instead means the shell never renders its default prompt at all.
  - **Second real bug found and fixed the same way**: the relative-path prompt initially always showed the `$sythrall:<absolute path>` fallback, even at the workspace root itself. Root cause — `portable-pty`'s ConPTY spawn does *not* reliably inherit `terminal-server`'s own working directory the way a plain Win32 `CreateProcess` call would (confirmed by hand: a trivial `cmd.exe` launched the same way inherited the cwd correctly, but the interactive `powershell.exe`/`cmd.exe` sessions spawned through the pty layer did not). Fixed by calling `CommandBuilder::cwd()` explicitly with the same root instead of relying on inheritance — now `$PWD.Path` on the very first prompt always matches `$root` exactly.
  - **Shell picker** — new `GET /terminal/shells` (unauthenticated, same reasoning as `/terminal/token`: exposes nothing sensitive, just which shell binaries exist for the sidecar's own OS) backs a dropdown next to the "+" button; `?shell=` on the WebSocket query string is checked against a strict allow-list server-side (`resolve_shell`) — the client's string is **never** passed straight to `CommandBuilder`, since that would be a remote-code-execution vector if the terminal token ever leaked.
  - **Tabs**: close (×) per tab, double-click to rename inline. Hiding the terminal *panel* no longer kills every session — matches real terminal apps (VSCode included): a build or long-running script left in a tab keeps running in the background while the panel is hidden, exactly like a minimized terminal window. Closing a specific tab's × is what actually kills that PTY session now.
  - **`@xterm/addon-search`** (Ctrl+F, prev/next/close) and **`@xterm/addon-web-links`** (URLs printed in the shell are clickable) — neither existed before, only `addon-fit` was wired.
  - **Copy/paste, VSCode/Windows Terminal convention**: `Ctrl+C` copies the selection instead of sending SIGINT when text is selected; without a selection it passes through as `^C` like always. `Ctrl+V` pastes the clipboard as input.
  - **Auto-reconnect** — a dropped connection (sidecar restarted, network blip) retries the same session up to 5 times with a short backoff instead of leaving a dead terminal.
  - **`ansimax`-powered welcome banner** (`utils/terminalBanner.ts`), same gradient/figlet-art wordmark and color palette as the `npm run dev` console banner, for one consistent visual identity. Real bug hit and fixed while building this: `ansimax` is written for Node CLIs — merely calling `gradient()`/`ascii.banner()` threw `process is not defined` in the browser (`vite build` doesn't catch this; it only surfaces at runtime), because its color-support detection reads `process.env`/`process.stdout` unconditionally. Fixed with a tiny shim (`utils/processShim.ts`, imported before `ansimax`) that defines a minimal `globalThis.process` — and sets `FORCE_COLOR=3` deliberately, since `ansimax`'s own TTY-detection would otherwise see no real `process.stdout.isTTY` and silently print plain, uncolored text, even though xterm.js renders truecolor ANSI perfectly.
  - Expanded the xterm theme from a bare `{background, foreground}` pair to a full 16-color ANSI palette matching Sythrall's own accent colors, plus cursor/selection colors.
  - Split-pane (side-by-side terminals) and scrollback surviving a full page reload were both considered and deliberately left out of this pass — neither was asked for beyond "feel like VSCode," and each is a sizable feature on its own.
- [x] **Terminal auth redesigned — static shared secret → session tokens (JWT), base for multi-user/cloud with no login yet**: the single-secret model above (256-bit CSPRNG, constant-time comparison, served only to loopback requests) was solid for "you and your own machine," but has no path to the multi-programmer, remote-server model Sythrall is headed toward. Rebuilt as a clean auth-server/resource-server split: `apps/api` (new `routers/auth.py`) becomes the sole token issuer; `services/terminal` stops generating its own secret and becomes a pure verifier — it doesn't care who issued a token, only that its signature and expiry are valid. That's exactly the shape the system keeps the day real login exists: `apps/api` signs tokens after a real login instead of for an implicit `"local"` user, and `services/terminal` doesn't change a line.
  - HS256 with a shared secret (not RS256) — no real identity authority exists yet to justify a keypair; the secret (`SYTHRALL_AUTH_SECRET`) is generated once by `scripts/dev-banner.mjs` (runs sequentially before `concurrently` starts the parallel dev processes, avoiding a generation race) and persisted to the root `.env`.
  - Claims: `sub` (`"local"` today), `scope` (`"terminal"` — defense in depth if this secret is ever reused for another token kind), `iat`/`exp` (1-hour lifetime).
  - **Real bug caught by the test suite, not code review**: `jsonwebtoken` v11 doesn't auto-select a crypto backend — without `features = ["rust_crypto"]` in `Cargo.toml`, every `encode`/`decode` call panics at runtime. A near-identical false start followed during end-to-end verification: re-running a stale pre-fix `target/debug/terminal-server.exe` reproduced the exact same panic, until it was rebuilt.
  - **Third real bug, only caught against the user's actual running dev server**: the frontend's token fetch was modeled on the *old* endpoint's relative-URL pattern (correct there, since Vite's `/terminal` proxy really does target the Rust sidecar's port). The new token is issued by `apps/api`, and every other fetch to that backend already bypasses Vite's proxy entirely via `getApiBase()` (which hits `:8420` directly in dev — Vite's own proxy entries for that backend all point at a dead `:8000`, invisible until now since nothing used a relative fetch against them). Fixed by switching to `getApiBase()`, matching the rest of the codebase.
  - Frontend token cache moved from a bare string in `sessionStorage` to `{token, expiresAt}`, read from the JWT's own `exp` claim, discarding it a few seconds before real expiry instead of reusing a stale token blindly.
  - Verified end-to-end against real `apps/api` + `terminal-server` processes on isolated ports with a raw WebSocket client: a valid token opens a real PTY session; a tampered signature, an expired token, a wrong `scope`, and plain garbage are all rejected with 401 — all 5 cases confirmed by hand, plus 5 new Rust tests and 3 new Python tests, all green.

### ✅ Phase 13 — Algorithmic Intelligence *(extends Phase 8's O/Θ/Ω engine, not a new architecture)*

Phase 8 already computes worst-case O, best-case Ω, and tight-bound Θ per function — a specific, standard application of asymptotic notation in algorithm analysis (matching the convention used by CLRS and most algorithms texts). Worth making explicit rather than implicit, since the general definitions are broader than that one use:

- [x] **Asymptotic notation reference**, surfaced wherever a Big-O result already appears: a collapsible `<details>` reference table above the Static panel's Big-O table (`panels/static.ts::_renderBigOTable`) covers all five symbols — O (upper bound), Ω (lower bound), Θ (tight bound), o (strict upper bound), ω (strict lower bound) — general definition first, honest that `o`/`ω` aren't computed (no reliable static heuristic distinguishes "strict" from the tight case). The Python hover tooltip (`_build_hover_python`) gets the same explanation as a one-line footnote under its O/Θ/Ω table. JS/TS hover intentionally untouched — it only computes O, not Θ/Ω, so the fuller legend doesn't apply there yet.
- [x] **Space complexity** alongside time complexity, built in Rust and Python from the same pass this time (`services/complexity/src/space.rs` + `static_parser.py::_infer_space_python`, both wired the same day) — same heuristic AST-based approach as the time engine (no execution), but the signal is *what auxiliary structure gets built*, not *how many times a loop runs*: a loop that only accumulates into a scalar (`total += x`) is O(1) space even though it's O(n) time. Detects growing collections (`.append`/`.add`/`.update`/`.insert`/`.extend`, or `d[k] = v` subscript-assignment) at loop-nesting depth (O(n) at depth 1, O(n²) at depth 2 — a matrix built in nested loops), nested comprehensions (`[[0 for _ in range(n)] for _ in range(n)]`), and recursion-stack depth (O(log n) for binary-split recursion reusing `bigo.rs`'s existing split detector, O(n) for linear recursion, since Python doesn't optimize tail calls). Byte-for-byte parity confirmed between the Rust and Python implementations on all 8 cases by hand. Wired into `/intel/hover` and `/intel/analyze` (Rust-first, Python fallback, same gate as Big-O) and a new **Space** column in the Static panel's Big-O table. Benchmarked with Criterion vs. real `_parse_python()` timing on the same synthetic files: 10 functions — 0.77ms vs 18.0ms (23.4×); 100 — 9.17ms vs 212.6ms (23.2×); 1000 — 254ms vs 2083ms (8.2×) — and reported honestly that adding this pass slowed `analyze_rich()` itself by 30–59% against its own prior baseline (two more full-body walks per function stack up), not just the win against Python.
- [x] **Recurrence relation recognition** for divide-and-conquer functions, **Rust-only** (`services/complexity/src/bigo.rs::resolve_master_theorem`) — deliberately not mirrored into the Python fallback (see below). Before this, a recursive function with no loop of its own (`merge_sort`, a recursive binary search) fell straight through every branch of the existing loop-depth heuristic to its generic default (`O(n)`, "base case"), because that heuristic only reasoned about loop nesting and a single `is_recursive` bool. Recognizes `T(n) = a·T(n/2) + f(n)` and resolves it via the Master Theorem's three cases, showing the recurrence itself (`T(n) = 2T(n/2) + Θ(n)`) alongside the resolved `Θ(n log n)` — not just the answer. `a` (subproblems per call) is its own small piece of reasoning, not a reused counter: it treats `if/elif/else` branches as mutually-exclusive alternatives (`max` across branches) and sequential statements as additive (`sum`), so `merge_sort`'s two unconditional recursive calls give `a=2` while a recursive binary search's two calls in mutually-exclusive `elif`/`else` branches correctly give `a=1` (`T(n)=T(n/2)+O(1)` → `Θ(log n)`, not `T(n)=2T(n/2)+O(1)` → `Θ(n)`). `f(n)`'s degree comes from whichever is larger: the function's own loop nesting, or — via a second pass over the file's already-analyzed functions — the Big-O of a helper it calls (`merge_sort` calling `merge()`, already resolved to `O(n)` on its own). 5 Rust tests (`rich::tests`) cover the real cases (`merge_sort`, recursive binary search, non-divide-and-conquer recursion). **Not ported to `static_parser.py`**: an initial pass did build full parity, but with the Rust sidecar as the primary path (running whenever available) and Python only a degraded fallback, maintaining two full implementations of this specific piece wasn't worth it — the pure-Python fallback now always reports `recurrence: None` for every function (confirmed by 4 Python tests) and keeps answering with the pre-existing generic loop/recursion heuristic, same as before this phase. Wired into `/intel/hover` (Rust-rich branch only — the row simply doesn't appear when the sidecar is down) and the Static panel's existing recursion badge tooltip — no new UI surface, reuses the hover that already existed for `recursion_note`.

### 🟡 Phase 19 — Machine Intelligence *(Assembly side of the language-philosophy table — integrate mature tools, don't rebuild them)*

Analysis of what code *becomes*, not just what it says. Each of these is its own serious project already solved well by dedicated open-source tools — the honest move is to embed those, not reinvent them:

- [x] **Assembly (x86-64) analysis-target support, first bullet shipped** — instruction/register/control-flow breakdown from raw `.s`/`.asm` snippets, exactly as scoped: pattern-matching on text, not a disassembler (that's the 2nd bullet below, explicitly deferred). Assembly never had any support in Sythrall before this — like Fortran in Phase 20, it's genuinely new in Rust, nothing to port. Treated as a **7th language plugin**, the same generalized mechanism Fortran already proved (Phase 24): `plugin.rs::builtin_manifests()` → `plugin_registry.py::extension_map()` → `static_parser.py::parse_file()` → `_LANGUAGE_HANDLERS["assembly"]`. Mnemonics (`mov`/`jmp`/`call`/...) are identical in both, so one classification table serves both syntaxes — only operand extraction and register-name matching differ (AT&T's `%` prefix is unambiguous; Intel has no sigil, so operands are checked against a fixed ~60-name x86-64 register list instead).

### ✅ Phase 20 — Scientific Intelligence *(Fortran, deepened past a single bullet point)*

Fortran as an analysis target, connected to the numeric stack Sythrall already ships with (numpy/scipy's compiled LAPACK/BLAS backends) — not a language Sythrall's own engine needs to be written in. Unlike C/C++/JS/TS (Phase 18), this is the first language port that doesn't replace a pre-existing Python implementation: Sythrall had zero Fortran infrastructure before this phase, so it was built directly in Rust (`services/complexity/src/fparse.rs`) from the start, using [`tree-sitter-fortran`](https://crates.io/crates/tree-sitter-fortran) v0.6.0. Same wiring pattern as `cparse.rs`: a new sidecar endpoint (`POST /parse/fortran`), a Python client wrapper (`parse_fortran_rust`), and a `static_parser.py` dispatch branch — no Python-side fallback, same as C/C++/JS/TS (degrades to `_unsupported()` without the sidecar).

Bumping in `tree-sitter-fortran` surfaced a real ABI incompatibility: the crate's compiled grammar targets language ABI version 15, which the `tree-sitter = "0.24"` Rust binding (already a dependency, shared by the C/C++ parsers) does not support (`LanguageError { version: 15 }` at runtime, not a compile error). Fixed by bumping `tree-sitter` to `"0.25"` — its runtime supports ABI 15 while remaining backward-compatible with the older grammars `tree-sitter-c`/`tree-sitter-cpp` already ship, confirmed by the full existing C/C++ test suite staying green after the bump.

- [x] **DO-loop / array-operation detection, vectorization & SIMD candidates** — `do_loop_depth` computed by walking nested `do_loop` AST nodes (real tree-sitter nodes, not a text heuristic like C's `infer_big_o_c`). A `vectorization_note` fires only for depth-1/2 loops where an array element on the assignment's left-hand side is subscripted by the loop's own control variable (`A(I) = ...` inside `DO I = ...`) — extracted via a `DO\s+(?:\d+\s+)?(\w+)\s*=` regex over the loop's source text, the one place this module falls back to text matching (the grammar's `loop_control_expression` internals aren't documented stably enough to navigate by field). Deliberately hedged, not a proof: the note text says outright that it doesn't verify iterations are actually independent — `A(I) = A(I-1) + 1` (a real sequential dependency) still matches the same shape, and the engine doesn't do cross-iteration data-dependency analysis for any language yet.
- [x] **Numerical algorithm recognition with domain-specific framing** — a triple-nested (`do_loop_depth >= 3`) loop containing an assignment to a doubly-subscripted array (`C(I,J) = ...`) whose right-hand side multiplies two other doubly-subscripted array references fires `numerical_algorithm_note`: *"Triple-nested DO loop ... shape matches classic matrix multiplication, O(n³). Candidates: SIMD, loop blocking/tiling, parallelization (OpenMP/coarrays). Domain: HPC/Numerical Computing."* — the exact framing this bullet asked for, not a bare Big-O label. Explicitly a shape signal: it does not confirm the indices actually form `C(i,j) += A(i,k)*B(k,j)`.
- [x] **BLAS/LAPACK usage detection** — every `CALL`/function-call target inside a procedure is checked against a curated (not exhaustive — the ask was detection, not a full ~1500-routine LAPACK catalog) list of Level 1–3 BLAS and common LAPACK routine stems (`GEMM`, `GEMV`, `AXPY`, `GETRF`, `POTRF`, `SYEV`, `GESVD`, etc.), matched with or without the S/D/C/Z precision prefix (`DGEMM`/`SGEMM`/`ZGEMM`/`GEMM` all match). Surfaced per-function as `blas_lapack_calls`, flagging where a project already leans on compiled numeric backends instead of reimplementing something those backends provide.
- [x] **Full stack wiring, not just the parser**: `PARSEABLE_EXTENSIONS`/`CODE_EXTENSIONS` (`.f`/`.f90`/`.f95`/`.f03`/`.f08`/`.for`), the `/static/languages` capability-discovery endpoint, the live-editor metrics bar (`metrics_live.py::_metrics_fortran`, a regex-only quick calculator — same tier as its C/C++ counterpart, not the real tree-sitter parser), and the frontend (`lang-fortran` badge color, `LANG_DISPLAY_NAME`, three new hedged badges in the Static panel's Big-O table — "SIMD?", "Matrix?", "BLAS/LAPACK" — each with the full note as its tooltip, same convention as Phase 16's "Type-1?" badge). Monaco has no built-in Fortran syntax-highlighting mode, so the editor's `EXT_LANG` map was left untouched for Fortran files (cosmetic gap, out of scope for this phase — same as the pre-existing untouched gap for `.c`/`.cpp`).
- [x] **A one-line grammar gotcha caught by tests, not shipped silently**: `tree-sitter-fortran`'s grammar reuses the exact string `"function"`/`"subroutine"` both for the named container node (with `_statements` children) *and* the anonymous keyword token (`SUBROUTINE`/`END SUBROUTINE`) — `node.kind()` alone can't tell them apart. Without an `is_named()` guard, every procedure was counted 3 times (the real container plus its own opening and closing keyword tokens). Caught immediately by the first extraction test (`detecta_subrutina_simple_sin_loops` expected 1 function, got 3), fixed with one added condition, documented in the same commit.
- [x] **Test coverage**: 12 new Rust unit tests (`fparse.rs`) covering plain-function/subroutine detection, DO-loop nesting → Big-O (0/1/2/3+ → O(1)/O(n)/O(n²)/O(n³)), the vectorization-candidate shape (positive and negative), the matrix-multiplication shape (positive and negative), BLAS/LAPACK name matching (with and without precision prefix), `USE` statement extraction, and call-graph edges between known subroutines. 7 new Python tests: 2 in `test_complexity_client.py` (sidecar-down → `None`, sidecar-up → finds the subroutine) and 5 in `test_static_analysis.py` (end-to-end through `/static/parse`, one per bullet plus a sweep confirming all 6 recognized extensions dispatch to the Fortran path) — run against the real sidecar `conftest.py` already rebuilds fresh, not mocked.

### ✅ Phase 21 — Security & Taint Intelligence *(pattern-based data-flow analysis, confidence-scored — not a SAST replacement)*

A gap the original 9-pillar pass missed entirely: nothing in Phases 13–20 looks at security. Direct continuation of the CS Engine's existing style — Phase 8/12's regex/grammar classifiers already prove "heuristic pattern + honestly-labeled confidence" works — applied to source→sink data flow instead of algorithmic shape. Nothing here should ever be presented as "this IS a vulnerability," only as a pattern worth a human's attention, with the evidence shown so the claim is auditable. CWE catalog v1 complete:

- [x] **Taint tracking within a single function** — a recursive, provenance-carrying walk resolves a value back to an untrusted source (`request.args`/`form`/`values`/`json`/`GET`/`POST`/`COOKIES`/`headers`, `input()`, `sys.argv`, `os.environ`/`os.getenv`) through assignments, string concatenation, f-strings, and `.format()`, tracking *whether* the taint was built via string construction (the actual SQLi/command-injection signal) vs. passed through raw. **Deliberately not cross-function** — interprocedural taint needs the call graph the Dependency Engine below doesn't build yet. **Ported to Rust the same day it shipped in Python** (`services/complexity/src/security.rs`), not left as a someday-item. Both covering the vulnerable and the safe/parameterized form of every check, byte-for-byte parity between the two confirmed by hand on every case.
- [x] **CWE catalog v1, 5 of 5 shipped**: SQL Injection (CWE-89) — fires only when the query is *built* via concatenation/f-string/`.format()`, so `cursor.execute("...%s...", (val,))` correctly produces no finding; Command Injection (CWE-78) — `os.system`/`os.popen` (always shell) or `subprocess.*(..., shell=True)`, `subprocess.run([...])` without `shell=True` correctly produces no finding; hardcoded credentials (CWE-798) — name+shape heuristic, file-level rather than per-function since that's genuinely where these live; **Path Traversal (CWE-22)** — `open(path)` needs the same "built via concatenation" signal as SQLi (`open(f"uploads/{name}")` fires, `open(config_path)` doesn't), `os.path.join(base, seg)` fires on any tainted non-first segment even unconcatenated, since joining a raw `"../etc/passwd"` is already the traversal; **Insecure Deserialization (CWE-502)** — `pickle.loads`/`pickle.load`/`marshal.loads` are unsafe by construction (no "safe form" exists, unlike SQLi/command injection), so they fire at Medium confidence even *without* provable taint and escalate to High when the argument does trace to a taint source; `yaml.load` fires unless called with an explicit `Loader=yaml.SafeLoader`/`CSafeLoader`.
- [x] **Confidence-scored findings** (High/Medium — Medium introduced by CWE-502's untainted-but-still-risky case, the first real use of that level), never a bare yes/no — mirrors the "both signals required" precedent from Phase 12's grammar classifier: a source alone isn't a finding, source *and* the concatenation/sink signal both firing is
- [x] **Evidence-tree finding schema** — category → CWE → severity → confidence → source → sink → line → recommendation, one shared shape for every finding. Surfaced in the **Static panel** and in the Python **hover tooltip**, Rust-only (`security.rs`, see Phase 18 — the Python taint-tracking implementation was deleted, not kept as a fallback; without the sidecar, findings degrade to an empty list) — **not yet the Problems Panel**: that tab is fed by per-keystroke lint markers, and security findings currently run on the same heavier `/static/parse` pass as WASM hints, which live in Static too, not Problems
- [x] **Two real bugs found and fixed the same week this shipped**, both via an independent audit, not self-caught: (1) reassigning a tainted variable to a safe literal (`cmd = request.args.get("x"); cmd = "ls -la"`) didn't clear its taint, producing a High-confidence false positive on ordinary defensive code; (2) a nested function reusing an outer variable's name leaked taint across scopes. Both fixed by making the taint walk scope-aware (`_own_scope_nodes` in Python, `walk_stmts_own_scope` in Rust — a generic AST walker variant that stops at nested `FunctionDef`/`Lambda` boundaries instead of descending into them), with regression tests in both languages. The Rust port built *after* both fixes never had either bug.
- [x] **Project-level Findings, aggregated** (Phase 22 slice) — `security_findings` across every file in a project, not just one at a time, surfaced in the Static panel's project view with the originating file shown per item, sorted by severity
- [ ] Explicitly out of scope, permanently: full exploit analysis (ROP, heap spray, use-after-free) — already correctly fenced off under Execution Intelligence (Phase 23 below) as "competes directly with mature SAST tools"; this phase stays inside that same boundary, just static and narrower

### ✅ Phase 22 — Code Quality Intelligence *(the Maintainability Index Phase 11 already ships, broken into its auditable parts, plus the smells one MI number can't express)*

`complexity-engine`'s Maintainability Index (Phase 11) already computed a Halstead Volume internally but only exposed it pre-baked into one formula. This phase surfaces the components that formula is built from, and adds the structural/naming/architecture smells a single MI number can't catch on its own:

- [x] **Halstead metrics, broken out** (`maintainability.rs::HalsteadMetrics`/`halstead_metrics()`) — Vocabulary (η1+η2), Length (N1+N2), Volume, Difficulty, Effort, their own struct next to the MI score instead of staying an opaque input to one formula. Refactoring `compute()` to take the pre-computed metrics instead of re-walking the suite itself actually **removed** a duplicate AST walk that existed before this phase — a real measured win (4.6–7.1% faster at 10/100 functions), not just new surface. **Rust-only, no Python fallback** — same boundary MI/CC/raw metrics have had since Phase 11 replaced `radon` outright; the degraded shape is `halstead: null`, not a slower Python recomputation.
- [x] **Structural smells** (`smells.rs`, Rust-only — see Phase 18): long function (LOC>50), excessive parameters (>5), deep nesting (any block type, depth>4), large class (methods>15 or LOC>300), god object (methods≥20 AND self-attributes≥10) — conventional Fowler/Martin thresholds, each smell carries its threshold and reasoning in the message, never a bare label. `duplicated logic` (AST-shape hashing) is explicitly deferred, not silently dropped — needs a normalization/hashing scheme that doesn't exist yet.
- [x] **Project Health dashboard**: 4 scores (Security/Quality/Complexity/Architecture) aggregated from `security_findings`/`structural_smells`/complexity/the circular-dependency detector at project scale — each score carries its formula and raw counts alongside it, never a bare number. Surfaced on the Dashboard and in the Static panel's project view, sharing one renderer between both.
- [x] **Naming smells** (`naming.rs`, Rust-only — see Phase 18): single-letter variable outside a loop/comprehension (parameters deliberately exempt — `def add(a, b)` is idiomatic and the name sits next to the signature, so flagging it would be noise, not signal), inconsistent snake_case/camelCase mix within one file (up to 3 examples of each style quoted in the message), a nested function binding a name already used in an enclosing scope (module global or an outer function's parameter/local) — intentionally conservative, flags only mechanically-checkable cases rather than "unclear name" judgment calls that would need an LLM to arbitrate. Counted separately from structural smells in the Quality score (`health.quality.naming`) since naming issues are lower-severity per occurrence than a god object or deep nesting.
- [x] **Architecture smells** (`routers/graph.py::_build_architecture_smells`, Python-only): coupling/cohesion per module, built on the import graph that already exists (Phase 6/14) — high efferent coupling (>15 internal imports, calibrated above `main.py`'s own 11 legitimate composition-root imports), unstable dependency (afferent ≥3 and instability Ce/(Ca+Ce) >0.5, Martin's metric), and the already-shipped circular-dependency detector reframed as one instance of a general layer-violation check (each cycle now also surfaces as a `circular_dependency` smell entry, not just its own separate graph). Python-only by design — the cross-file import graph these smells need only exists in `graph.py`, never ported to Rust (that's Phase 18's own separate "Graph Engine" item, deliberately not tackled here) — the mirror-image case of Halstead being Rust-only because *its* data only exists in Rust.

### 🟡 Phase 23 — Execution Intelligence *(runtime instrumentation — a different kind of tool than everything above)*

Everything in Phases 1–22 is static analysis: source text in, facts out, no execution required. This phase is architecturally different — it needs a running process, ptrace/eBPF, or live packet capture, which is why it stayed an uncommitted "long-term" idea bucket for a long time. Numbered here to be honest that it's a real destination, not to claim it's close:

- [x] **Empirical Big-O validation for Fortran's matrix-multiply shape** — the first real slice of this phase, and much narrower than the other four bullets below (no ptrace/eBPF/packet capture needed, just `gfortran` and `std::process::Command`). Born from a direct ask: rather than adding Fortran to Sythrall's own engine as decoration ("Fortran matters" with no concrete task), this makes Fortran do real, functional work inside the engine for the first time — compiling and running actual Fortran to check Sythrall's own static claim, not just detecting Fortran in someone else's project.
  - New `services/complexity/src/fortran_bench.rs` — `complexity-engine`'s first-ever process execution (confirmed via full-workspace grep: zero `std::process::Command`/`Command::new` anywhere in this binary before this). Compiles a **fixed ~25-line Fortran kernel that Sythrall itself writes** — never the user's code, never anything uploaded — a generic `n×n` matrix multiply parameterized by `n` as a command-line argument (`GET_COMMAND_ARGUMENT`, compiled once with `gfortran -O2`, run 4 times at calibrated sizes). This is the scope boundary that keeps the execution surface tiny: there is no code path anywhere in this module that compiles or runs anything other than this one fixed template, so it never inherits the arbitrary-code-execution risk a general sandbox would need to solve.
  - Sizes (`300, 450, 600, 800`) were calibrated by hand against this dev machine's `gfortran`/Windows `CPU_TIME` resolution (~15.6ms granularity) so even the smallest measurement clears the clock's resolution instead of reporting a false zero — confirmed live before committing to the constants, not guessed. Each size is run 3 times and the **minimum** is kept (standard micro-benchmarking practice: OS/scheduling noise can only ever add time, never subtract it, so the minimum tracks the kernel's real cost more closely than a mean would).
  - `fit_exponent()` — a plain least-squares fit on `(ln n, ln seconds)`, no new dependency, `None` below 2 valid points. The response's `note` field states explicitly, same hedging discipline as `purity.rs`/Type-1 (Phase 16): this confirms the general shape scales as O(n³), it does **not** validate any specific user function's performance.
  - Deliberately no external timeout crate, no manual process-polling: the only thing this module ever executes is 100% Sythrall-authored, with sizes it chooses itself — there is no untrusted input on the execution path for a hang to come from. Documented explicitly in the module as a boundary that would need its own design if this ever runs anything less trusted.
  - `TempWorkDir` — a `Drop`-guarded temp directory (`fs::remove_dir_all` best-effort) so a failed compile/parse never leaves an orphaned `.f90`/binary in the system temp dir, same "no silent leaks" discipline already applied to the Force Graph memory leak earlier this session.
  - New endpoint `POST /execution/validate-matmul` (no body — kernel and sizes are fixed for this first version), a new Python router `apps/api/routers/execution.py` (deliberately **not** added to `static_analysis.py`, whose own docstring says "análisis estático... SIN IA" — this endpoint executes code, a different category), and `complexity_client.py::validate_matmul_bigo_rust()` (30s timeout override, matching the tiered-timeout convention already used for whole-project scans).
  - Frontend: a "Validar empíricamente" button appears next to any function's `Matrix?` badge (`numerical_algorithm_note`, Phase 20) in the Static panel. Since the kernel is generic rather than per-function, one click validates for the whole session — the result renders as a shared `n^X.XX` badge (green within ±0.3 of 3.0, amber otherwise) on every matching row, with the full hedge in its tooltip.
  - 7 new Rust tests (`fortran_bench::tests`) — 4 pure-math tests for `fit_exponent` (no `gfortran` needed), plus 3 that check `gfortran` availability and either run the real end-to-end compile+execute (confirmed working on this dev machine, exponent measured ≈2.9–3.6 across runs, comfortably inside the `2.0..4.0` sanity band chosen to catch a broken implementation without demanding lab-grade precision on a shared, noisy dev machine) or exercise the graceful-degradation path if `gfortran` isn't present — same "runs for real when available, degrades honestly when not" discipline as every other optional dependency in this codebase. 2 new Python tests (`test_complexity_client.py`) mirroring the same available/unavailable split.
  - New `examples/fortran/scientific_intelligence_demo.f90` (added alongside Phase 20, reused here) — `MATMULT` in that file is exactly the shape that triggers this validation, so it doubles as the manual end-to-end test fixture.
- [x] **Memory visualizer (stack/heap/data/bss) — shipped as static analysis, NOT the live-process inspection this bullet's own wording originally implied.** Confirmed explicitly with the user before building anything, not assumed: attaching a debugger to an arbitrary running process would be a genuinely new, unprecedented risk surface for this engine (inspecting/executing third-party code under a debugger) — `fortran_bench.rs`'s own module doc already draws this exact line ("running third-party code needs its own sandbox design, don't silently extend this"). What actually shipped: `services/complexity/src/memlayout.rs`, a new module that classifies every C/C++ variable into stack/data/bss **by its declaration in the AST** — correct by construction from C/C++ storage-class rules (never ambiguous, not a guess): a local variable without `static` is stack; a `static` local or a file-scope variable is data (has an initializer) or bss (doesn't); `extern` declarations are skipped (no storage in this translation unit); function prototypes aren't variables at all.
  - **`"heap"` is deliberately not a variable region — it's a separate allocation-site list**, a pedagogically more correct model than tagging the pointer itself: `int *p` is a stack variable regardless of what it points to; what actually lives on the heap is the memory `malloc`/`new` hand back. `allocations` records every `malloc`/`calloc`/`realloc`/`free` call (C) and `new_expression`/`delete_expression` (C++, real tree-sitter-cpp node kinds, not a regex guess), with the target variable resolved only in the two common, unambiguous patterns (`T *x = malloc(...)`, `x = malloc(...)`, `free(x)`) — no data-flow tracking beyond that, `variable: null` rather than a guessed value when the pattern doesn't match.
  - Shares the tree `cparse.rs` already parses for functions/classes/etc. — `memlayout::build(root, source)` takes the same `Node`, never parses the same text twice. Wired into `CParseResult` as a new `memory` field, riding along in the existing `/parse/c`/`/parse/cpp` responses exactly like `call_graph`/`wasm_hints` already do — no new endpoint.
  - Every result carries an explicit `note` hedge, same honesty discipline as `fortran_bench.rs`'s own: *"static declaration classification, not a measurement of a running process."*
  - 15 new Rust tests (`memlayout::tests` — one per region-classification case, `extern`/prototype exclusion, `malloc`/`free`/`new`/`delete` variable resolution including the unresolvable case, and an end-to-end region-count check) and 5 new Python tests (`TestMemoryLayout` in `test_static_analysis.py`, exercising the real sidecar end-to-end) — all 89 pre-existing `test_static_analysis.py` tests pass unmodified.
  - Frontend: `StaticParseResult` gains an optional `memory_layout` field (`client.ts`); `static.ts` gets a new `_renderMemoryLayout()` — a color-coded list grouped by region plus an allocations list, same `.metric-section` convention as `_renderCallGraph`/`_renderWasmHints`, deliberately **not** a box-and-arrow animated diagram (that level of visualization is already named separately as Phase 29's "Execution Path Simulator" — not reinvented here). New CSS in `static-addon.css` (`.st-mem-*`), reusing existing `--info`/`--ok`/`--muted`/`--orange` tokens rather than inventing a new palette. **365 Rust tests total (350 previous + 15), 563 backend tests total (558 previous + 5), Clippy/`ruff`/`tsc`/`vite build` clean.**
- [ ] Concurrency analyzer (races, deadlocks, mutex/atomic misuse) — needs real execution or tools like ThreadSanitizer, not AST inspection
- [ ] OS engine (threads, paging, scheduling, IPC) — needs kernel-level tracing
- [ ] Network analyzer (TCP/TLS/QUIC/WebSocket) — needs packet capture; this is a Wireshark-shaped tool, not a static analyzer
- [ ] Security analyzer beyond pattern detection (ROP, heap spray, use-after-free exploitation) — competes directly with mature SAST tools (Semgrep, CodeQL, Bandit); the realistic version folds into Phase 21 above as "detect the pattern + explain the CWE," not a full exploit-analysis engine

## Where this is going, next: a platform, not just a core

Phases 13–23 above are one arc — Sythrall's own core learning to read code from the algorithmic structure underneath it down to the machine. Phases 24–30 below are a second, different arc, added 2026-08-30 from a direct, detailed ask: **the core doesn't have to know everything itself.** A real enterprise stack is rarely one language or one system — it's an ERP, a SQL Server instance, spreadsheets exported as CSV, and a C/C++ system that's been running since before most of the team was hired. The honest answer isn't teaching the Rust core every format and system that could ever show up; it's a typed extension boundary the core exposes, so the user activates only what their own stack actually needs:

```
                    Sythrall
                        │
                Extension System
                        │
        ┌───────────────┼───────────────┐
        ↓               ↓               ↓
    Connectors    Format Extensions   Language /
   (SQL Server,      (.xlsx, .csv,    Modernization
    Postgres,         .parquet,        Extensions
    GitHub, S3...)     .xml...)      (C/C++, COBOL,
                                       Fortran...)
        │               │               │
        └───────────────┼───────────────┘
                         ↓
             The user activates only
              what their stack needs
```

This second arc changes what Sythrall is honestly describable as. "Reads code, computes Big-O" (the framing the Phase 13–23 section above opens with) is still accurate for that arc alone, but Phases 24–30 point somewhere bigger: a **Software Intelligence & Modernization Engine**, not a linter and not a static-analysis tool that happens to have plugins bolted on. The shape, end to end — source code and its dependencies in; parsed and analyzed through the same Computer Science Intelligence Phases 13–23 already built (mathematics, security, architecture); a Modernization Graph (Phase 25) turning those findings into per-piece Keep/Refactor/Replace/Rewrite/Migrate candidates; a migration validated (Phase 26) before it's ever proposed as done, not just generated and handed over; the result benchmarked and reported, never asserted:

```
                    PROJECT
                       │
             ┌─────────┴─────────┐
             ↓                   ↓
        SOURCE CODE          DEPENDENCIES
             │                   │
             └─────────┬─────────┘
                       ↓
              COMPUTER SCIENCE
                 INTELLIGENCE (Phases 13–23)
                       │
       ┌───────────────┼────────────────┐
       ↓               ↓                ↓
   Mathematics      Security       Architecture
   (Big-O/Θ/Ω)      (CWE/taint)    (graphs/smells)
       │               │                │
       └───────────────┼────────────────┘
                       ↓
              MODERNIZATION (Phase 25)
                       │
          ┌────────────┼────────────┐
          ↓            ↓            ↓
        Rust          Zig       Modern C++
          │            │            │
          └────────────┼────────────┘
                       ↓
              VALIDATE (Phase 26) → BENCHMARK → REPORT
```

Every language in the table above earns a slot in this pipeline because of what it specifically contributes, never because it exists: Rust is where the deterministic analysis lives; C/C++ is both an analysis target and the raw material Modernization reads; Zig only enters a component when Rust's own abstractions are themselves the wrong fit (ABI/memory control, C interop — never "because it's fast"); Assembly is the last rung, reached only after Rust and Zig/C have both been tried and profiling still shows a real gap; Fortran is the numerical-kernel step in a pipeline that starts as a Python prototype and ends orchestrated by Rust; Python stays the home for AI/ML/scientific work, not a legacy the migration is trying to erase. Every bullet from here to Phase 30 is 🔴 — vision, confirmed directly with the user, not a commitment or a timeline. Phase 24 already shipped a real plugin interface (3 bullets below) before this broader framing existed; everything else here is genuinely new ground, sequenced so each phase's own honesty note says exactly why it isn't built yet, the same discipline this document has held everywhere else.

### 🟡 Phase 24 — Extensibility Platform *(the plugin/capability interface Phases 25–30 all build on top of)*

Every phase above adds directly to Sythrall's own codebase — reasonable while one person maintains it, but each of Phases 13–23 is realistically a plugin's worth of scope on its own. This phase is the boundary that lets that work happen outside the core without every analyzer becoming a `routers/` file Sythrall itself has to own forever. What shipped here (3 bullets below) was scoped deliberately small — no marketplace, no sandboxing, no third-party trust model, because none of that had a reason to exist before a second real plugin. **That's no longer the ceiling**: the vision below organizes future plugin work into 5 typed categories instead of one flat "plugin" bucket, because a SQL Server connector, a `.xlsx` parser, and a CWE detector are genuinely different shapes of thing, even though `plugin.rs`'s manifest interface (shipped) is generic enough to describe all of them without changing:

- 🔌 **Connectors** — connect Sythrall to an external system: SQL Server, PostgreSQL, Oracle, MySQL, GitHub, GitLab, S3, Azure. None shipped yet.
- 📄 **Format Extensions** — understand a file format Sythrall's own parsers don't: `.xlsx`, `.csv`, `.parquet`, `.json`, `.xml`, `.pdf`, `.avro`, `.protobuf`. None shipped yet.
- 🧠 **Analysis Extensions** — add intelligence over data a Connector/Format Extension already exposed, or over code the core already parses. Named retroactively: everything Phases 13–23 already shipped (CWE/Security, Graph, Dependency, Data-Structure, Numerical) already *is* this category, just not filed under the name until now.
- ⚙️ **Language Extensions** — add specialized language support. Also named retroactively: the 6 languages `plugin.rs` already serves (Python/C/C++/JS/TS/Fortran) are this category; Fortran is the proof case the 2nd bullet below already cites.
- 🔄 **Modernization Extensions** — understand a legacy format/language, detect what's incompatible with a modern target, then propose or execute a *validated* migration — never a blind convert. This is the category Phase 25 below develops in full; nothing here duplicates that phase, this bullet only names where it fits in the taxonomy.
- [x] **Plugin manifest + capability interface** — new `services/complexity/src/plugin.rs`: a purely declarative `PluginManifest` (`id`, `category`, `needs: &[Capability]`, `extensions`, `parser`, `features`, `builtin`) with zero dependency on the parser modules it describes — a manifest declares what a plugin does, it doesn't live inside the implementation. `builtin_manifests()` returns the 6 built-in language plugins (python/c/cpp/javascript/typescript/fortran), served over a new `GET /plugins/manifests`. Caught and fixed a real staleness bug while porting the content: the Python entry's `parser` field still said `"Python ast (stdlib)"`, a leftover from before Phase 18 — the real parser has been `rustpython-parser` in the Rust sidecar since then, with the stdlib `ast` module only running in the no-sidecar fallback skeleton. Corrected while rewriting, not left stale.
- [x] **One plugin type shipped end-to-end** — Fortran (Phase 20) is the proof case, exactly as this bullet suggested. `apps/api/services/static_parser.py::parse_file` no longer dispatches through a literal `if ext == ".py": ... elif ext in (".f", ...): ...` chain: extension → language-id resolution now goes through `services/plugin_registry.py::extension_map()`, itself derived from the same manifests `plugin.rs` serves. Fortran is no longer "another branch hardcoded into `static_parser.py`" — it resolves through the identical mechanism as the other 5 languages, not a special case. The actual `_parse_python`/`_parse_c`/`_parse_cpp`/`_parse_js`/`_parse_ts`/`_parse_fortran` functions are untouched — only *how* one gets selected changed, which is exactly why all 552 pre-existing backend tests kept passing unmodified: strong evidence the new dispatch is behaviorally identical to the old one, not just superficially similar.
  - **Manifests are fetched once at Python startup**, same timing and the same accepted degradation profile as `HAS_COMPLEXITY_ENGINE` (`check_complexity_engine_sync()`, already computed once at import time in `main.py`) — if the sidecar isn't up in that exact instant, `plugin_registry.py` falls back to a local `_FALLBACK_MANIFESTS` constant (the identical 6-language content, frozen as a floor, not a second hand-maintained source of truth competing with `plugin.rs`) for the rest of that process's life. - [x] **C/C++ modernization candidates, first slice shipped: manual memory management** — new `services/complexity/src/modernization.rs`, genuinely the first real engine in this phase, not another vision bullet. Builds directly on Phase 23's `memlayout.rs`: zero new AST work, pure reinterpretation of the `allocations` it already tracks. Pairs each acquisition (`malloc`/`calloc`/`realloc`/`new`) with a release (`free`/`delete`) of the *same variable name* in the same file — two patterns, both with evidence attached, never a bare label: **`manual_memory_raii`** (both sides found — medium confidence, suggests a smart pointer in modern C++ or Rust's ownership model, either would make a forgotten/duplicated `free` a compile error instead of a runtime bug) and **`unmatched_allocation`** (acquisition with no release found anywhere in the file — high confidence, either a real leak or ownership transferred somewhere this heuristic can't follow, suggests Rust ownership specifically since that model forces the transfer to be explicit). **Honest about its own limit, not silent**: matching is by variable name within the whole file, not real per-scope tracking — the same simplification `memlayout.rs::resolve_target_variable` already accepted, documented again here rather than pretending this is more precise than it is. Wired into `CParseResult` as a new `modernization` field, riding along in the existing `/parse/c`/`/parse/cpp` responses exactly like `memory`/`call_graph` already do — no new endpoint, no new network round-trip. Rust pointer-ownership analysis across function boundaries, raw-pointer-without-malloc patterns, and unsafe-cast detection are explicitly **not** attempted in this slice — real future work, not silently folded in.
- [x] **C/C++ modernization candidates, second pattern shipped: double-free detection** (2026-08-31) — extends `modernization.rs` with **`double_release`**: any variable released (`free`/`delete`) more than once in the same file. Unlike the first slice's 2 patterns, this isn't "could be modernized" — it's a real correctness bug already present (undefined behavior in C/C++), reported at maximum confidence since counting repeated releases has none of the cross-scope ambiguity that name-based acquire↔release pairing carries (documented as an accepted limit in the first slice). Points at the *repeated* release's own line, not the first release or the original allocation, since that's where the double-free actually happens. Suggests `rust_ownership` specifically — Rust's compiler rejects moving or freeing an already-moved value, making this class of bug unwritable, not just easier to avoid. 3 new Rust tests, 1 new Python test — all pre-existing tests for the first slice's 2 patterns pass unmodified. **404 Rust tests total (401 previous + 3), 578 backend tests total (577 previous + 1), Clippy/`ruff`/`tsc`/`vite build` clean.**
- [x] **C/C++ modernization candidates, third pattern shipped: unsafe-realloc-reassignment detection** (2026-08-31) — extends `memlayout.rs`'s `AllocationSite` with a new `reassigns_same_pointer: bool` field, computed in `extract_allocations` by comparing `realloc`'s first argument against the variable it's assigned back to, then `modernization.rs` reads it to flag **`unsafe_realloc_reassignment`**: the classic `p = realloc(p, size)` bug — if `realloc` fails it returns `NULL`, and reassigning that directly to `p` overwrites the only reference the program had to the original allocation, an instant leak with no way back. Like `double_release`, this is a real bug already present, not a stylistic suggestion, so it's reported at high confidence; unlike the acquire/release patterns, no cross-scope ambiguity is even possible here since it's a single-call check on `realloc`'s own arguments. Suggests `rust_ownership` — `Vec`'s internal reallocation can't be told to overwrite its own only handle, so this bug class has no Rust equivalent to write in the first place. 2 new Rust tests in `memlayout.rs`, 2 new Rust tests in `modernization.rs`, 2 new Python tests — all pre-existing tests for the first two slices' 3 patterns pass unmodified. **408 Rust tests total (404 previous + 4), 580 backend tests total (578 previous + 2), Clippy/`ruff`/`tsc`/`vite build` clean.**
- [x] **C/C++ modernization candidates, fourth pattern shipped: use-after-free detection** (2026-08-31) — the first pattern in this file that walks the AST directly instead of only reinterpreting `allocations`, because "a use" isn't an allocation site. New `use_after_free_candidates()` in `modernization.rs`: for each release (`free`/`delete`) with a resolved variable, it searches for the first later occurrence of that same identifier inside the window *[release line, next acquisition of the same variable)* — reassigning to fresh memory closes the window, since the pointer becomes valid again. An occurrence only counts as a "use" if it isn't the left-hand side of an assignment (`p = NULL` is exactly the safe idiom this pattern must not punish, not a use) and doesn't coincide with another known allocation-site line for the same variable (so a second `free` isn't double-reported here *and* as `double_release`). Reported at `medium` confidence, not `high` like the other bug patterns — this is a genuine textual/line-order heuristic with no real control-flow analysis, so a `free` inside one branch followed by an unconditional use can be a false positive if the branches were actually mutually exclusive; that limit is stated plainly in the module doc, not hidden. Required exposing `memlayout::walk_flat`/`text_of` as `pub(crate)` (reused rather than duplicated, since `modernization.rs` already depends on `memlayout`'s types) and changing `analyze_c_cpp`'s signature to take the parsed `root`/`source` that `cparse.rs` already had on hand. 4 new Rust tests (real parsed C source, not synthetic `AllocationSite` literals, since this pattern needs actual AST structure), 3 new Python tests — all pre-existing tests for the first three slices' 3 patterns pass unmodified (13 existing Rust test call sites updated via a thin `analyze()` test wrapper that feeds them an empty AST, since none of them exercise this new pattern). **412 Rust tests total (408 previous + 4), 583 backend tests total (580 previous + 3), Clippy/`ruff`/`tsc`/`vite build` clean.**
- [ ] **Legacy-format modernization candidates** — old SQL dialect/schema → modern SQL; deprecated library/API usage → its current replacement; a legacy data format → a modern one — same "detect the gap, propose, don't silently convert" shape as the C/C++ case above, generalized to non-code legacy artifacts once Phase 24's Connectors/Format Extensions exist to read them in the first place.
- [ ] **Modernization Report as a first-class output, richer than today's flat candidate list** — a real per-piece graph (Keep/Refactor/Replace/Rewrite/Migrate) spanning more than memory-management patterns, same "evidence, not a verdict" discipline Phase 21's security findings already established and this slice's own `reasoning`/`confidence` fields already start.

The C/C++ work above is real (5 patterns now: manual-memory-RAII, unmatched-allocation, double-release, unsafe-realloc-reassignment, use-after-free — the last one an admitted heuristic, not a certainty, given it has no real control-flow analysis behind it), but this phase is still far from done: no concrete architecture decision has been made about how a proposed migration gets *validated* (matching Phase 26 below) before Sythrall would ever suggest applying it — that's real design work for whenever a later slice tackles it, not assumed now. Raw-pointer-without-malloc, unsafe-cast detection, real control-flow/branch analysis, and anything beyond memory-management patterns remain unattempted.

### 🟡 Phase 26 — Algorithm Validation Engine *(generalizes Phase 23's Fortran matmul validation beyond one language, one algorithm shape)*

Phase 23 already shipped a narrow, real proof of this idea: `fortran_bench.rs` compiles and runs a fixed Fortran kernel to check whether a statically-predicted O(n³) shape actually measures as O(n³). This phase is that same pattern, generalized — a **static claim** (from the Big-O engine, Phase 13) compared against an **empirical measurement** from a controlled, Sythrall-authored experiment, not the user's own code:

```
Static claim (e.g. "O(n²)")
        ↓
Generate a controlled synthetic experiment
        ↓
Execute an isolated benchmark — same safety boundary fortran_bench.rs
already documents: never the user's code, only a template Sythrall itself
authors and controls end to end
        ↓
Fit a mathematical model to the measurements
        ↓
Compare: static ≈ empirical?
        ↓
"Predicted O(n²), measured n^1.94 — High confidence"  or
"Predicted O(n³), measured n^2.01 — ⚠ discrepancy detected"
```

This needed genuinely new statistics, not a reuse of `fit_exponent`: polynomial growth (`n^k`) is linear on a log-log plot (`ln time` vs `ln n`), which is what `fit_exponent` already fits; exponential growth (`bⁿ`) is linear on a semi-log plot (`ln time` vs `n` untransformed) instead — applying `fit_exponent` to exponential data would produce a meaningless number that keeps drifting upward as the chosen N range grows, since exponential growth eventually outpaces any fixed polynomial. - [x] **Sixth kernel: O(n log n), a hand-written Assembly mergesort — and a real, serious stack-frame bug caught by exhaustive verification, not shipped by luck** (2026-08-31). `services/complexity/src/mergesort_bench.rs` compiles and runs `kernels/validate_mergesort.s`, an **iterative bottom-up mergesort** — deliberately not recursive (recursion is already `fib_bench.rs`'s job above; this kernel exists specifically to demonstrate O(n log n) via log₂(n) merge passes, each O(n), a much simpler thing to hand-write correctly than a recursive quicksort). `temp`, an auxiliary buffer the same size as `arr`, comes from a minimal C driver (`kernels/validate_mergesort_driver.c`, same reason as `validate_sum_squares_driver.c`: a raw `.s` object can't `malloc`) which also **verifies the array actually ended up sorted before reporting a time**, printing `-1` instead if not — a broken kernel must never silently feed a plausible-looking number into the exponent fit.
  - **The bug, found the hard way**: the first version wrote its locals (`width`, `i`, `left`, `mid`, ...) starting at `-4(%ebp)`. That's wrong — `push %ebx`/`push %esi`/`push %edi` happen *after* `%ebp` is set, so `-4`/`-8`/`-12(%ebp)` are where those three saved registers actually live, not free space. Every local write was silently clobbering a saved register; the epilogue's `pop` then restored garbage into it before `ret`. This was invisible at `-O0` (the caller reloads everything from its own stack, never trusting a callee-saved register to survive a call) but caused a real, reproducible segfault at `-O1` and above, where GCC *does* cache values like the `arr` pointer in a callee-saved register across the call, correctly trusting the cdecl ABI to preserve it — exactly what this bug violated. A first non-guarded reproduction attempt (heap padding, GDB watchpoints on an old Windows GDB 7.6.1) produced contradictory, unreliable signals; the bug was only pinned down precisely by allocating `arr`/`temp` via `VirtualAlloc`+`VirtualProtect(PAGE_NOACCESS)` so the buffer's end is a hard guard page — turning "sometimes corrupts something eventually" into an immediate, deterministic fault at the exact offending write. Fix: locals now start at `-16(%ebp)`, leaving `-4`/`-8`/`-12` alone. Re-verified for correctness across every size from 0 to 1,000,000 at `-O0` through `-O3` before trusting the kernel again — not just at the one size that happened to crash first.
  - **O(n log n) is not a clean power law**, unlike every other kernel's shape so far: the log-log exponent `fit_exponent` (reused as-is, no new statistics needed) measures for `n·log(n)` data isn't a fixed number — it lands a bit above 1.0 (measured ≈1.07–1.11 on this machine) and drifts slightly with the chosen size range, since `n log n` isn't literally `n^k` for any fixed `k`. The response's `note` says this plainly rather than implying false precision; the frontend still anchors the "close enough" check at exponent 1.0 (same ±0.3 band as the other roughly-linear kernels) because that's still enough to catch a badly broken merge (e.g. one that degenerates to O(n²)), just without claiming lab-grade precision on the number itself.
